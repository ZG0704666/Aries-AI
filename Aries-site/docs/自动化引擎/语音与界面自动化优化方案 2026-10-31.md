## 1. 语音转文本（ASR）链路

### 1.1 现状分析

**模块与模型**：`speech/SherpaSpeechRecognizer.kt`（935 行）+ `SherpaSpeechRegistry.kt`（共享实例注册表），native 层 `app/src/main/cpp`（sherpa-ncnn JNI）。

| 环节 | 现状（行号证据） | 评估 |
|---|---|---|
| 模型 | `sherpa-ncnn-streaming-zipformer-bilingual-zh-en-2023-02-13`，enc/dec/joiner bin 合计 ≈134.6MiB（`createRecognizer()` L344） | 2023 年初社区模型，**无公开 CER，训练语料"internal dataset"许可不明**（调研文档 §2.7），是现役最大隐患 |
| 采集 | AudioRecord `VOICE_COMMUNICATION` 16k/mono/PCM16，buffer=min×2（L812-838） | 近讲可用；无声纹降噪前端 |
| 解码 | `greedy_search` + numActivePaths=4，numThreads=4，useGPU=false（L399-403） | ncnn 运行时只支持贪搜；4 线程未针对机型调优（社区实测 14M 级小模型单线程 RTF 0.046 反而最快，多线程对小模型常为负优化——待真机实测） |
| 端点 | `enableEndpoint=false`（L412），按住说话、松手定稿、60s 上限（L165） | 设计合理；但**无 VAD**，静音段全部进解码，免提/长句场景无分句能力 |
| 标点 | 模型不带标点/ITN，热词未启用（hotwordsFile=""，L416） | 标点依赖上层处理，专有名词/联系人名识别无加权手段 |
| 工程 | 会话执行器串行 + 代数丢弃 + 尾音排空（R-02~R-08 已修）；模型缓存原子交付 + SHA-256 清单（R-04，`ModelCacheManifest`） | 稳定性基座良好，替换模型时这套机制可完全复用 |

### 1.2 2025-2026 替代方案对比（调研结论）

> 详细数据见《对话系统/离线ASR模型调研 2026-10-31》（21 个候选、体积/CER/许可已核到官方页面）。本轮联网增量核实补充如下：

| 方案 | 体积（int8） | 流式 | 中文精度量级 | 端侧可行性（2026 实测口径） | 结论 |
|---|---|---|---|---|---|
| **现役 ncnn 双语 2023-02-13** | 134.6MiB | ●原生 | 无公开数据（社区模型） | 可用 | 许可最不明，建议限期替换 |
| **sherpa-onnx streaming-zipformer-zh-int8-2025-06-30** | ≈160M | ●原生 | aishell-1 **1.91**（公开榜最优流式） | 桌面 RTF 0.15，低端机需实测 | **效果首选**；商用前必须过 WenetSpeech（71% 语料）非商业限制审计 |
| **sherpa-onnx small-ctc-zh-int8-2025-04-01** | **25M** | ●原生 | 未公布→必测 | RTF 0.038-0.045 | **体积首选**，HF 标 apache-2.0 但语料未披露 |
| **⭐增量：sherpa-onnx-x-asr-480ms-streaming-zipformer-transducer-zh-en-punct-int8-2026-06-05** | ≈128MB | ●原生（480ms 块） | 未公布→必测 | 第三方产品实测 CPU 实时、首字延迟≈69ms 量级 | **中英双语+内嵌自动标点**，与现役体积相当、直接补齐标点短板，是现役 ncnn 双语的直接继任候选（许可与 CER 需核实/实测） |
| streaming paraformer 双语 int8 | ≈226M | ●原生 | 未公布 | RTF 0.15 | 许可最干净（Apache-2.0 已核）的中英混说选项 |
| SenseVoice-Small int8 | 228M | ○非流式 | 弱于上者（VAD 分段后整段解码） | 真机 RTF≈0.06（快） | 不满足按住说话首字体验；**许可注意：权重是 FunASR Model License，非标准 OSI 许可（本轮核实与调研文档"Apache-2.0"表述冲突，需人工复核模型卡）** |
| Qwen3-ASR-0.6B | ≈940M-1.9G | ◐动态窗口流式（流式 CER 恶化 18-26%） | 0.6B 档最强（Fleurs-zh 2.88） | 真机 CPU RTF 0.53 / 1.8-1.9GB，低端机不可行 | 旗舰溢价位，不进主推 |
| FireRedASR2 / Fun-ASR-Nano | 740M-1.2G | ◐/○ | 开源 SOTA（普通话 2.89） | 服务器方案（32GB 卡起步） | 不适用端侧 |

**VAD/标点生态增量**：TEN VAD（腾讯，2025-06 开源 ONNX，2025-07 已并入 sherpa-onnx 官方）比 silero-vad 语音端点延迟低数百 ms、Android so 仅 ~532KB（真机 RTF 0.049-0.057），是后续"免提模式/自动分句"的首选前端。

### 1.3 选型建议

1. **运行时：sherpa-ncnn → sherpa-onnx**（+15MB libonnxruntime.so 代价）。理由：ncnn 生态锁死 2023 年模型，2025-2026 全部新模型只发 onnx；不换运行时则永远停留在"许可不明 + 无标点"的现役模型。
2. **模型分档（A/B 后定档）**：
   - 中英混说 + 自动标点（主推候选）：x-asr-480ms-streaming-zh-en-punct-int8-2026-06-05（≈128MB，与现役体积持平）；
   - 纯中文效果档：streaming-zipformer-zh-int8-2025-06-30（公开 CER 最优）；
   - 低端机体积档：small-ctc-zh-int8（25M，APK 可降至 ~45MB 量级）。
3. **许可 gate 前置**：WenetSpeech/AISHELL-2 审计不通过时，退守 paraformer 双语（Apache-2.0）或 small-ctc（向作者确认语料）。现役 ncnn 模型替换本身就是出清最大许可风险。
4. **不建议**：Qwen3-ASR / FireRedASR / Fun-ASR-Nano / Moonshine-zh（体积、流式或许可任一不满足）；SenseVoice 仅作"非流式对照组"。

### 1.4 预期收益与落地路径

**收益**：中文 CER 进入公开可度量区间（aishell-1 ≈1.9-2.0 量级 vs 现役未知）；自动标点内嵌（去掉上层拼接逻辑）；模型许可风险出清；体积档位可选（-110MiB ~ +25MiB）。

**路径**（对齐调研文档 §6 A/B 清单，避免重复建设）：
1. 抽象 `SpeechRecognizer` 接口，sherpa-onnx 作为第二实现并接（现会话执行器/缓存清单机制全部复用）；
2. 用调研文档 §6.3 语料集（10 类 × ≥30 句）+ §6.4 判据（首字 ≤400ms P95、松手→final ≤300ms P95、低端机 RTF ≤0.6）在真机 A/B 三档模型；
3. 通过后默认切换 + 保留 ncnn 回退一版；随后评估 TEN VAD 接入做"免提连续对话"模式。

## 2. 界面自动化链路

### 2.1 现状：逐环节架构

```
任务输入
 └─ 智能应用启动（正则+包名解析，UiAutomationAgent.kt L679-811）
     └─ 每步循环（≤maxSteps=100）：
        ① 采集：截图（ScreenshotManager：虚拟屏/Shizuku/无障碍三路）+ UI 树（无障碍 dump；Shizuku 树被 L45 硬编码禁用；虚拟屏=纯视觉）
        ② 构建：system prompt（PromptTemplates L36-109）+ 截图 base64 + UI 树文本（截断 3000 字）
        ③ 调用：AutoGlmClient（非流式）或 LocalMnnInferenceEngine（本地 MNN），重试 ≤3
        ④ 解析：ActionParser 提取 <answer> do(action=...) 文本协议，修复 ≤2 次
        ⑤ 执行：ActionExecutor 三通道（虚拟屏注入 > Shizuku input > 无障碍手势），失败修复 ≤1 次
        ⑥ 收尾：固定 delay（stepDelayMs=160 + 动作延迟）→ 回到 ①
```

### 2.2 逐环节薄弱点与优化方案

| # | 环节 | 现状与证据 | 问题 | 优化建议 | 预期收益 | 优先级 |
|---|---|---|---|---|---|---|
| 1 | 提示词 | **"错误示例"与"正常示例"完全相同**（PromptTemplates.kt L97-105，均为 `do(action="Tap", element=[500,150], desc="点击顶部搜索")`） | 模型无从习得错误边界，格式修复循环被无谓触发 | 改为真实反例（混入自然语言、缺引号/缺参数）+ 一行硬约束说明 | 解析失败率↓，省 1-2 次修复调用/异常 | **P0·本轮已修** |
| 2 | 提示词 | screenW/H 仅用于算比例（L53-57）；坐标 0-1000 约定只有一句话（L86）；"每个动作先做截图再决策"（L90）与框架控制流不符（截图由框架执行，模型无法主动截图） | 坐标系/截图缩放信息缺失影响定位精度；误导性指令浪费 token | 补充"截图已按比例缩放、坐标按 0-1000 归一化"说明；删除/改写"先做截图"句 | 定位准确率↑，token↓ | P1 |
| 3 | 采集 | VD 路径截图直接 `screenshotPngBase64NonBlack()` 无压缩（ScreenshotManager.kt L105-125）；`screenshotMaxSizeKB=150`/`screenshotScalePercent=80` 仅无障碍路径生效（待验证） | 每步全屏 PNG base64 可达数百 KB，token 与上行延迟放大 | VD 路径复用缩放+JPEG/降质压缩管线 | 每步 token 成本与耗时显著下降（估 -30%~-60%，需实测） | **P1** |
| 4 | 采集 | `ENABLE_SHIZUKU_UI_TREE=false`（UiAutomationAgent.kt L45）；虚拟屏模式 UI 树恒为占位符（L277） | 纯视觉驱动，小字/密集列表定位弱 | ①恢复 Shizuku/无障碍树与视觉融合（树给 resourceId/文本，图给布局）；②引入 Set-of-Mark：截图上叠加元素编号再送模型，模型输出编号代替坐标 | 复杂页面动作成功率↑（业界 GUI agent 共识做法） | P2 |
| 5 | 调用 | `useStreamingWithEarlyStop=true`（AgentConfiguration L173）与 `parallelScreenshotAndUi`（L180）**声明了但未实现**：主循环用非流式 `sendChatResult`（UiAutomationAgent.kt L1179），截图与 UI 树串行获取 | 配置与行为不符；每步白白等待完整回复结束 | ①接 AutoGlmClient 既有 `sendChatStreamResult`（L229 已存在），检测到动作括号闭合即早停；②截图与 UI 树协程并行 | 每步模型等待时间↓（流式早停通常可省 30%+ 尾部等待，需实测）；采集耗时≈取二者 max | **P1** |
| 6 | 调用 | 执行失败修复提示只传动作原文：`buildActionRepairPrompt(currentAction.raw, ...)`（UiAutomationAgent.kt L579），**异常信息只进了日志没进 prompt**（L551） | 模型盲猜失败原因，修复成功率低 | 把执行异常 message/失败阶段（点击失败/输入校验失败/超时）结构化注入修复提示 | 修复一次成功率↑，减少"失败→修复→再失败→任务终止" | **P1** |
| 7 | 执行 | VD 通道注入后恒 `return true`：`injectTapBestEffort(...)` 返回值被忽略（ActionExecutor.kt L784-790；back/home/swipe 同型 L426-431/455-460/954-966） | 注入失败被当成功，浪费一步模型调用且污染历史 | 传递注入结果；失败走既有修复循环 | 步数有效率↑ | **P1** |
| 8 | 执行 | 敏感词跳过返回 false（ActionExecutor.kt L525-528/L721-724），与"执行失败"同语义 | 触发无关的模型修复循环，且修复也不会成功 | 区分"安全跳过"终态（返回成功+标记，或直接 finish-with-reason） | 避免无效修复调用；安全语义更清晰 | P2 |
| 9 | 收尾 | 固定 `delay(stepDelayMs + 动作延迟)`（UiAutomationAgent.kt L663）；已有 `awaitWindowEvent` 事件等待但未用于"界面是否变化"判断 | 页面早稳时白等；页面未变时下一步拿到旧截图，模型易重复同一动作 | 动作后对比截图指纹（如 pHash/字节长度+包名+窗口事件时间），未变化时在下一步 user 消息注入"界面无变化"提示 | 每步平均等待↓；死循环步骤↓ | **P1** |
| 10 | 循环 | `take_over`/`note`/`call_api`/`interact` 直接判任务失败（UiAutomationAgent.kt L472-479） | 需要用户介入的任务被整体终止，无法续跑 | 挂起等待用户输入（复用 `Control.confirm` 通道）后 resume | 交互闭环，任务完成率↑ | P2 |
| 11 | 循环 | `finish` 即成功（L427-430），无完成校验 | 模型可能幻觉宣布完成 | 可选验证步：finish 后再截一帧让模型自检或做 UI 断言（配额允许时启用） | 任务真实完成率↑ | P2 |
| 12 | 线程 | A4：`Thread.sleep` 在输入校验重试（PhoneAgentAccessibilityService.kt L787/L832，`verifyTextApplied`/`trySetTextOnNode` 非 suspend 链） | 在协程调用链上阻塞线程（可能主线程） | 整链 suspend+delay 改造（涉及 setTextOnElement/setTextOnFocused 调用方，结构改动） | 消除 ANR 风险 | P2（结构性） |
| 13 | 架构 | 两套自动化接口并存：`do(action=...)` 文本协议（UiAutomationAgent）与 `AIToolHandler` 工具注册（ToolRegistration.kt 877 行，tap/click_element/set_input_text 等语义重叠） | 双份维护、行为不一致（如 VD 注入校验只有一套有） | 中期合并为单一工具协议（优先 function-calling 结构化输出，解析失败率天然低于正则） | 维护成本↓，解析鲁棒性↑ | P2 |
| 14 | 死代码 | M3：`attachAnimatedRing`/`attachAnimatedBorderRing`（MainActivity.kt L4245-4541）**无调用方**，绘制逻辑全被注释、仅剩两个 ValueAnimator 快慢互调无限空转；N5：`runDemo`（PhoneAgentAccessibilityService.kt L865）无调用方 | 无限动画空耗 CPU/电量；死代码噪音 | 删除 | 省电、可读性 | **P0·本轮已删** |

### 2.3 预期收益（自动化侧）

- P1 批次（5 项）落地后，单步耗时预计下降 30%+（流式早停 + 截图压缩 + 去无效修复），token 成本同步下降；步数有效率提升（注入校验 + 界面变化检测）。
