## 6. 语音输入完整链路

### 6.1 按下、录音和 partial

```text
长按 VoiceRecordButtonHandler
  → detectDragGesturesAfterLongPress.onDragStart
  → InputBar.onVoiceStart
  → MainActivity.ensureAudioPermission
  → beginVoiceSession() 分配 sessionId
  → VoiceSessionController.begin()
  → InputState.VoiceRecording(false)
  → SherpaSpeechRecognizer.startListening()
  → AudioRecord 16 kHz / 单声道 / PCM 16-bit
  → acceptSamples + while (isReady) decode
  → onPartialResult
  → MainActivity 校验 sessionId
  → VoiceRecording → VoiceRecognizing
  → 输入文本与波形更新
```

### 6.2 上滑与取消

```text
onDrag 收到纵向 dragAmount.y
  → change.consume()
  → totalDy 累加
  → totalDy < 进入阈值：isCancelling=true
  → 已进入取消区后 totalDy > 退出阈值：isCancelling=false
  → VoiceSessionController.onUpdateCancelState()
  → VoiceRecording/VoiceRecognizing.copy(isCancelling)
  → voicePresentation = Cancelling
  → 胶囊红色 + “上滑取消”
  → 松手时手势层依据自己的 isCancelling 调 onCancel
  → 恢复原输入文本、清空发送标记、状态 Idle
  → recognizer.cancel()，不请求 final
  → sessionId 失效，迟到回调被忽略
```

取消展示和松手决策分别保存在全局会话状态与手势局部状态中。两者必须保持同向更新；后续修改不要只改其中一处。

### 6.3 正常松手和发送

```text
非取消区松手
  → onVoiceEnd
  → VoiceRecording/VoiceRecognizing → VoiceFinalizing
  → 启动 8 秒 finalizing 看门狗
  → stopListening()
  → onFinalResult
  → consumePendingSend() 恰好消费一次
  → 状态 Idle、清理会话
  → 自动标点
  → sendMessage()
```

注意：底层 `stopListening()` 的尾音解码缺陷仍然存在，见风险 R-02。

## 7. 本次 Bug 根因与修复不变量

### 7.1 根因

原实现中：

1. 首个 partial 将 `VoiceRecording` 切为无取消字段的 `VoiceRecognizing`。
2. `MainActivity.onUpdateCancelState` 只处理 `VoiceRecording`。
3. `voicePresentation` 也只有 `VoiceRecording(isCancelling=true)` 能映射为红色取消态。
4. `VoiceRecognizing` 会隐藏普通录音提示。

因此会出现“手势层已经判定取消，松手也可能取消，但按住期间不红、不显示提示”的状态分裂。先上滑再收到 partial 时，也会被 `VoiceRecognizing` 覆盖回非取消展示。

Pager 嵌套滚动只处理横向分量，不是该现象的主因。

### 7.2 当前修复

- `VoiceRecognizing` 与 `VoiceRecording` 都能携带 `isCancelling`。
- `VoiceSessionController.onUpdateCancelState` 同时支持两种按住状态，拒绝在 `VoiceFinalizing` 等终态重新打开取消态。
- `onPartialResult` 从 `VoiceRecording` 迁移时继承取消标记。
- Activity 不再自行复制局部状态，而是读取控制器最新状态。

### 7.3 后续不得破坏的不变量

1. 只要手指仍在按住且会话未收尾，partial 不得清除取消状态。
2. 一旦进入 `VoiceFinalizing`，迟到拖动不得把状态改回识别或取消。
3. 取消路径不得设置或消费“松手发送”标记。
4. 旧会话的 partial、final、error、振幅均不得污染新会话。
5. 长按触发阈值与上滑取消阈值保持独立。
6. 录音激活时 Pager 用户滚动保持禁用，正常结束后恢复。

### 7.4 当前阈值

| 参数 | 资源值 | 当前 64dp 胶囊对应值 | 用途 |
|---|---:|---:|---|
| `m3t_input_bar_voice_cancel_enter_height_percent` | 125 | 80dp | 从未取消进入取消区 |
| `m3t_input_bar_voice_cancel_exit_height_percent` | 90 | 57.6dp | 从取消区退回发送区，形成滞回 |

不要仅凭一次主观手感继续降低阈值；先按 VOI-01 至 VOI-06 验收。

## 8. 底层语音链路风险清单

### 8.1 P0：优先修复

#### R-01：当前工作树没有实际 ASR 模型

证据：`app/src/main/assets/sherpa-models/` 只有 `README.md`，模型文件被 `.gitignore` 排除。当前代码固定寻找：

```text
sherpa-ncnn-streaming-zipformer-bilingual-zh-en-2023-02-13/
  encoder_jit_trace-pnnx.ncnn.param
  encoder_jit_trace-pnnx.ncnn.bin
  decoder_jit_trace-pnnx.ncnn.param
  decoder_jit_trace-pnnx.ncnn.bin
  joiner_jit_trace-pnnx.ncnn.param
  joiner_jit_trace-pnnx.ncnn.bin
  tokens.txt
```

影响：干净构建的 APK 即使包含 native 库，也无法保证语音可用。

建议：明确发布模型来源、版本、七个文件的长度与 SHA-256；在构建或发布流程中显式注入并校验，不要只检查 `.so` 是否存在。

#### R-02：停止录音后未排空尾音解码

位置：`SherpaSpeechRecognizer.stopListening()`。

当前顺序是 `inputFinished()` 后立即读取 `recognizer.text`。`inputFinished()` 只补尾音并标记输入结束，不会自动完成剩余 decode。

影响：短语音可能缺少结果，长语音可能丢尾字。

正确顺序应基于同一串行识别上下文：

```text
停止采集并等待读取循环退出
  → inputFinished()
  → while (isReady()) decode()
  → 读取最终 text
  → 恰好一次 onFinalResult
  → 释放本会话资源
```

不要在调用线程与仍在运行的录音协程上并发执行这套流程。

#### R-03：录音 Job、AudioRecord 和 native Stream 存在跨会话竞态

当前录音协程在 `finally` 中通过共享成员 `audioRecord` 释放资源，停止/取消只 `cancel()` Job而不等待退出。

可能交错：旧会话取消 → 新会话创建 AudioRecord → 旧 Job 的 finally 释放新 AudioRecord。旧 Job 也可能继续向同一个 native recognizer 写入音频。

建议：使用单线程识别执行器或 actor 独占会话；每个 Job 捕获自己的 AudioRecord；开始新会话前确保旧 Job 完全退出；会话 generation 贯穿底层回调；不得在持锁状态下直接调用 UI listener。

#### R-04：模型缓存完整性不足，native 加载失败可能终止进程

当前只检查文件存在且长度大于零，复制中断后的大于零部分文件可能被视为完整。部分 native 加载路径会 `exit(-1)`，Kotlin `try/catch` 无法兜底。

建议：临时目录完整复制 → 校验长度/哈希 → 原子 rename；模型版本进入目录名；排除大模型备份。native 错误转译若必须修改第三方代码，应单独立项并先取得用户批准。

### 8.2 P1：紧随 P0 处理

| 编号 | 风险 | 建议 |
|---|---|---|
| R-05 | 新会话使用 `reset(false)`，可能复用上一会话 Stream/decoder/encoder 状态 | 独立按住说话会话评估 `reset(true)` 或新建 Stream，并做连续重录验证 |
| R-06 | native 对象只依赖 `finalize()` 回收 | 在一方 `SherpaNcnn` 包装中提供幂等 `close()`/`AutoCloseable`，确保 Job 结束后确定性释放 |
| R-07 | `MainActivity` 与 `AutomationViewModel` 可能各加载一套模型 | 合并长期模型所有者或明确共享生命周期，避免双份 native 内存 |
| R-08 | 录音协程异常可能只走 finally，不通知上层且不清 `isListening` | 统一终态处理，异常时保证资源释放、状态复位和一次 error 回调 |
| R-09 | 无最大录音时长；每个音频块都可能复制完整累计文本 | 增加时长上限、结果读取降频和长录音压力测试 |
| R-10 | 自动标点回调脱离语音会话，旧结果仍可能自动发送 | 将 final 后任务绑定 session/generation 或可取消 Job |

### 8.3 P2：性能与兼容性

- 阻塞 `AudioRecord.read()` 与 CPU 解码共用 `Dispatchers.Default`，建议隔离采集阻塞和推理执行。
- 振幅每个非空音频块都切 Main，建议限制到约 20–30Hz，再按实机负载调整。
- `ret == 0` 时无退避，异常设备上可能形成紧密循环。
- 主链路 `enableEndpoint=false`，没有实际 Silero VAD 调用；RMS 仅用于波形。
- 音频目前直接流式传递，没有临时 PCM/WAV 文件需要清理；模型缓存不是临时音频文件。
- 权限主要依赖调用方，底层公开入口自身防御不足。

### 8.4 推荐实施顺序

1. 先建立可测试的会话执行器和终态契约。
2. 在同一串行上下文中实现停止 drain、取消不产出 final、旧会话隔离。
3. 使用 `reset(true)` 或新 Stream，补确定性 close。
4. 修复模型交付、原子复制和哈希校验。
5. 合并模型所有者，增加最大时长和回调降频。
6. 每阶段单独编译，并由用户执行对应真机回归。

### 9.1 推荐顺序

1. **中文识别效果优先**：先测 `sherpa-onnx-streaming-zipformer-zh-int8-2025-06-30`。
2. **体积和内存优先**：测 `sherpa-onnx-streaming-zipformer-multi-zh-hans-2023-12-12` INT8。
3. **中英混读或方言优先**：测流式 Paraformer INT8，但先确认内存峰值和 RTF 可接受。
4. 25MiB small CTC 只作为极端体积约束下的实验项，不作为“必然更准”的替代。

sherpa-onnx 官方 Android 文档给出的完整运行时约 7.2MB，其中 `libonnxruntime.so` 约 5.8MB；文档估算 sherpa-ncnn 运行时约 1.6MB。模型变小不代表 APK 和运行内存一定同比变小。

### 9.2 A/B 测试要求

使用同一设备、同一 AudioRecord 参数、同一批音频和同一尾音处理逻辑，至少记录：

- 中文 CER；若比较英文则记录英文 WER，不混用指标。
- 首字延迟、partial 稳定时间、松手到 final 的尾延迟。
- RTF，区分采集、推理和定稿耗时。
- Java 堆、native 堆和总 PSS 峰值。
- 连续十分钟录音的温升、降频和耗电表现。
- 安静、近场噪声、远场、快速语速、中英混读、数字、专有名词和应用指令语料。
- 至少覆盖短句、尾字易丢句和 30 秒以上长句。

模型许可证必须同时检查运行时、转换后权重、原始 checkpoint 和训练数据集；不能仅凭 sherpa-onnx 代码为 Apache-2.0 就认定所有模型可自由商用。

### 10.2 本次实际修复的差异

1. 吸附从动画实际值 `value` 改为参考使用的最近目标 `targetValue`。
2. `catchUp` 在启动吸附协程前生效，减少松手后交还 Pager 的一帧跳变。
3. 松手形变在滑块接近目标后恢复，阈值沿用参考的范围×0.025；额外增加 500ms 上限，避免旧实现曾出现的永久等待。
4. 程序吸附不再逐帧制造新的速度挤压，只让拖动残留速度衰减到零。
5. 可见页签保持 1x，只有供滑块采样的透明副本放大到 1.2x。
6. `TabSlot` 增加 Capsule 裁剪。
7. 按下时的零位移不再误触边缘振动。

### 10.3 不要误改的设计

- 当前 Pager 直接以实时分数驱动胶囊，跟手链路不需要再经过 `snapshotFlow` 中转。
- Pager 自己的 fling 已处理速度、decay 和吸附；不要为胶囊另行添加一套与参考不一致的 `animateDecay`。
- 页签槽位使用相同的 `weight(1f)`，吸附整数索引对应这些实际槽位的中心；它不是脱离布局的任意屏幕等分点。
- `HorizontalPagerScrollConnection` 只限制嵌套滚动的横向分量，不是完整的方向角仲裁器。
- 录音期间通过 `drawerGesturesEnabled=false` 禁用 Pager，是避免语音纵向取消与主页横向滑动互相抢夺的现有措施。

### 10.4 尚未做设备验证的差异

- 500ms 有界形变等待在不同帧率设备上的主观手感。
- 使用 `targetValue` 吸附在快速连续反向拖动时是否符合预期。
- 可见层不再放大后，文字、图标与滑块折射的视觉关系。
- 主题强调色与参考固定蓝色的差异是产品主题决策，不应在未确认时硬编码替换。
- RTL 并未在本次专项中完整对齐，若需支持应单独设计和验证。

### 15.2 新会话执行模型要点

1. **单线程会话执行器**：识别、解码、排空、终态派发全部串行运行在专用 `sherpa-ncnn-session` 线程；stop 请求与采样循环不再并发交错。
2. **每会话独占资源**：AudioRecord 与 listener 挂在各会话对象上，旧会话 finally 块只释放自己的 AudioRecord，跨会话竞态（R-03）消除。
3. **generation 隔离**：会话代数贯穿所有回调派发；旧会话迟到的 partial/final/error/振幅整组丢弃（不变量 4）。
4. **尾音排空**（R-02）：`stopListening()` 只发出停止采集请求并立即返回；`inputFinished() → while (isReady()) decode() → 读取最终文本 → 恰好一次 onFinalResult` 由会话任务串行执行，主线程不再读取 `recognizer.text`。
5. **取消不产出 final**（不变量 3）：cancel 路径与排空期间的 cancel/被替换都会先标记终态，杜绝迟到 final。
6. **新流**（R-05）：每次 `startListening` 会话开始时 `reset(true)` 重建流，不复用上一会话 decoder/encoder 状态。
7. **统一终态**（R-08）：会话任务整体 try/catch；异常时资源释放（finally）、状态复位与恰好一次 error 回调。
8. **确定性释放**（R-06）：`shutdown()` 捕获引用后把 native close 排入会话队列，与在途会话串行。
9. **小项顺带**：`ret == 0` 空读增加 10ms 退避（第8.3节 P2“紧密循环”问题的最低成本缓解）；振幅回调统一经主线程派发器。

### 15.3 行为差异需真机确认的点

- `stopListening()` 后 `isListening()` 在排空完成前保持 true（旧实现立即 false）；final 到达的相对时序不变或更完整。
- 秒级极短语音现在有尾音排空，final 文本应不再丢尾字（原 R-02 现象）。
- 端点分支保留旧行为（当前配置 `enableEndpoint=false`，不可达）。

### 17.2 提交后自检发现的缺陷（已修复）

`sha256Hex` 中 `MessageDigest.digest()` 被调用了两次：该调用在返回摘要的同时会**重置** MessageDigest，第二次调用返回的是空输入哈希（`e3b0c442...`），导致清单内所有 SHA-256 元数据无效而静默通过（启动校验只比对长度，属设计选择，因此行为无影响，但哈希列全部失真）。

修复：函数移入 `ModelCacheManifest.sha256Hex`（单次 digest 调用 + 复用字节数组），`ModelCacheManifestTest` 新增 2 例回归（"hello" 标准摘要比对、128KiB 大文件流式比对并断言不等于空输入哈希）。测试 7/7 通过。

未受影响范围：清单机制（长度校验）行为、原子交付路径、既有 5 例清单测试（修复后共 7 例）。
