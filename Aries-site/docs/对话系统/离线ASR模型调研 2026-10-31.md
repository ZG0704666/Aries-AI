# 离线/准流式中文 ASR 模型调研（Android 按住说话 · 2026-10-31）

> 调研口径：**中文优先移动端、完全离线、APK/缓存体积敏感、低端机可跑、按住说话（push-to-talk）要求原生流式**（按下即出 partial、松手快速出 final）。
> 结论* 本报告所有体积/RTF/CER 数字均标注来源为本次实际访问过的官方页面（见文末引用清单）；核实不到的字段一律写"**未能核实，需实测**"，不负责验证。
> 备注：sherpa-ncnn 部分量级模型文档里官方现役双语模型是现役规模——即当前在用的 `streaming-zipformer-bilingual-zh-en-2023-02-13`，本次已把它的确切体积核到 bin 级（见 §2.7）。

## TL;DR
1. **中文效果优先**：首选 sherpa-onnx `streaming-zipformer-zh-int8-2025-06-30`（~160M，原生流式，流式 CER aishell-1 1.91 / WenetSpeech dev 5.71），备选 `streaming-zipformer-ctc-zh-int8-2025-06-30`（155M，RTF 更低）；两者都踩 multi-zh-hans 混炼语料的许可疑点（WenetSpeech 占 10.0k/14.1k 小时且官网限"非商业目的"下载），商用前必须过许可证审计（§5）。
2. **体积/低端机优先**：首选 `streaming-zipformer-small-ctc-zh-int8-2025-04-01`（**25M** int8，RTF 0.038–0.045，HF 卡自称 apache-2.0，但中文 CER 与训练语料均未公布→必须实测）；次选 multi-zh-hans transducer int8（~69M，RTF 0.088）；极限体积走 sherpa-ncnn `zh-14M`（tar 22.2MiB）。
3. **中英混说优先**：首选流式 paraformer 双语 int8（~226M，Apache-2.0/ModelScope，无 timestamps、支持方言）；次选 9 语种 zipformer 2025-02-10（≈323M，官方文档未收录 + 训练配方未核实→风险高）；现役 ncnn 双语（bin 合计 134.6MiB，语料"internal dataset"不明）反而**许可最不透明**。
4. 运行时包袱：sherpa-onnx Android arm64 ≈ **19.7MB**（libonnxruntime.so 15M + libsherpa-onnx-jni.so 3.7M）vs sherpa-ncnn ≈ **4.4MB**；换 sherpa-onnx 需接受 +15MB 左右的这个代价，但仍可容纳任何 ≤70M 的 int8 模型。

## 2. 逐候选细项

### 2.1 streaming-zipformer-zh-int8-2025-06-30（multi-zh-hans zipformer-LARGE）
- **来源/文档**：https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html （raw rst: `docs/source/onnx/pretrained_models/online-transducer/zipformer-transducer-models.rst`）
- **体积**：fp32/fp16/int8 三档齐发；int8 = decoder fp16 4.9M + encoder int8 154M + joiner int8 1.0M ≈ **160M**（ls -lh 原文）。
- **指标**（icefall RESULTS.md，18th epoch，BPE 2000，"Streaming on zipformer-Large"段，与该 ckpt `yuekai/icefall-asr-multi-zh-hans-zipformer-large` 对应）：
  - 流式 Transducer 贪搜：alimeeting eval/test 26.83/28.74，aishell-1 dev/test 1.75/**1.91**，aishell-2 3.84/**4.12**，aishell-4 17.83，magicdata 3.23/**2.71**，kespeech 7.31/3.16/**8.69**，WenetSpeech dev/meeting/net **5.71/7.91/8.54**
  - 流式 CTC：aishell-1 1.71/**1.97**，aishell-2 3.89/4.06，WenetSpeech dev/meeting/net 6.11/8.13/10.62
  - 同 ckpt 也给了 Offline Transducer 行（aishell-1 1.33/1.38 等）用于参考上限
- **RTF**：桌面 **0.15**（sherpa 文档样例）。低端机 RTF 未能核实。
- **流式语义**：原生流式 transducer；PR/训练代码 `icefall egs/multi_zh-hans`。
- **许可**：権重无独立 license 字段（icefall 代码 Apache-2.0），**训练集 14,106 小时**（见 §5）——其中 **WenetSpeech 10,000 h（71%）官方限"非商业目的"下载**，AISHELL-2/AiShell-4/MagicData/KeSpeech 等另一部分需要各自条款复核。**结论：商用高风险，需逐条审计后才能定案。**
- **按住说话适配**：★★★★★ —— 唯一同时满足"效果 best + 体积 ≤200M + 原生流式"的模型。首字延迟由 chunk 配置决定；松手到 final 只剩 joiner 的延迟，无模型级尾惩罚。

### 2.2 streaming-zipformer-zh-xlarge-int8-2025-06-30
- 726M + 8.1M + 1.5M ≈ **736M**，桌面 RTF 0.46。RESULTS.md 该段（"streaming on zipformer-xl"，~700M 参数）**只发布 Offline 贪搜一行**（aishell-1 1.22/1.31，WSpeech 5.15/5.85/6.89），**流式行没有数字**。体量超标 1.3×，不适合本场景，仅作"效果天花板"参考。

### 2.3 streaming-zipformer-ctc-zh-int8-2025-06-30
- model.int8.onnx **155M**，桌面 RTF 0.14。同 RESULTS.md 的流式 CTC 段（指标见 §1 #3）。CTC 的 partial 会带 blank/重复处理的东西，需要做 CTC 标准化；首字延迟很小。⚠️ 文档还提到 `sherpa-onnx-zipformer-ctc-zh-int8-2025-07-03` —— 那是**离线** CTC（非流式），不是本候选，埋在排除表。

### 2.4 streaming-zipformer-small-ctc-zh-int8-2025-04-01（**体积优先首选**）
- **来源/文档**：https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-ctc/zipformer-ctc-models.html （raw rst 核到 ls -lh 明细）
- **体积**：int8 目录 `total 51992KB≈50.8MB`；核心 `model.int8.onnx = 25M`、`bbpe.model 249K`、`tokens.txt 13K`；fp32 版 `model.onnx=87M`。
- **指标**：byte-BPE vocab 1000，仅中文。**CER 未公布**（multi_zh-hans RESULTS.md 无小模型条目 → 需实测）。
- **RTF**：桌面 int8 样本 **0.038 / 0.045**。
- **许可**：HF 卡 yaml `license: apache-2.0`（README.md 首行已核实）。但卡内无训练数据说明（仅"Please refer to ./export.sh for model config"）；训练语料未知，若复用 multi-zh-hans 混炼数据则连带风险（§5）。
- **按住说话适配**：★★★★☆。体积 25M + RTF 0.04 的组合是在低端机上可能做到 RTF≈很高实时性的候选；风险集中在：(a) 未公开 CER；(b) 25M 小模型在"尾字丢/热词/专有名词"上的退化幅度未知。

### 2.5 streaming-zipformer-multi-zh-hans-2023-12-12（transducer）& -ctc-2023-12-13
- transducer int8：67M + 1.2M + 1.0M ≈ **69M**，RTF **0.088**；CTC int8 ≈ **68M**，RTF **0.078**。
- **文档明说** 2023-12-13 版**训练数据 = multi_zh-hans 14k 小时混炼**（PR icefall#1369），2023-12-12 transducer 同属该 recipe 家族。
- RESULTS.md 只给了这批 69M 模型**非流式**榜（zipformer ~69M：aishell-1 dev/test 2.91/3.04、aidatatang 3.36/3.83（CTC 2.86/3.36）、WSpeech dev 9.32）。流式行未发布 → 使用时按"69M 非流式 CER 的近似下限 + 需实测流式劣化"预估。
- 许可：⛔ 同 §2.1 语料链。

### 2.6 sherpa-onnx-streaming-zipformer-zh-14M-2023-02-23（onnx）与 ncnn 对应版
- onnx：训练于 **WenetSpeech**，int8 enc 21M + dec int8 1.8M（fp32 dec 7.2M），joiner 未列全（ls 输出截断），合计 ≈23–24M。ncnn 版 tar.bz2 **22.17MiB**，样例 RTF 0.121–0.131（4 线程）。
- 许可：WenetSpeech 数据限制链上（CC BY 4.0 + 非商业下载 + 音频版权在原始作者）。
- ⚠️ 14M 参数的极限体积模型，**官方无 CER**，只能实测。适合"体积极致走量"的兜底选项，作为体积优先档的第三选项。

### 2.7 现役 ncnn 双语 `streaming-zipformer-bilingual-zh-en-2023-02-13`
- **bin 级体积已核实**（HF repo，GitHub 官方资产与 HF blob 一致）：encoder 127,364,056 B + decoder 6,412,296 B + joiner 7,350,724 B ≈ **134.6MiB**；`tar.bz2=123.58MiB`。
- 上游 `pfluo/k2fsa-zipformer-chinese-english-mixed`，sherpa-ncnn 官方文档原话："**contributed by the community and is trained on tens of thousands of some internal dataset**" → 训练语料、权重许可**均无信息**。这是现役方案最大的**许可证阴影**。
- ncnn 生态现状：2023-02 之后 k2 基本只发 onnx，ncnn 适用面锁死（§0）。若换 sherpa-onnx 保留这颗模型，需要模型重导出（ncnn→onnx）——**sherpa-onnx 未提供该双语模型的 onnx 版**（onnx 双语是另一个社区模型，见 §2.10）。
- 按住说话适配：★★★（现役基线）。partial 可实时；小问题：模型训练年份早、语料不明，噪声/尾字场景未验证。

### 2.8 sherpa-ncnn-streaming-zipformer-small-bilingual-zh-en-2023-02-16
- 每 chunk 变体：enc 37.4–38.3M + dec 6.1M + joiner 6.9M ≈ **50.4MiB**（root/32、64、96 三个目录全套）；tar.bz2 140.6MiB。
- 官方文档点名：chunk=96 版跑得快、但说话后才有结果（显式延迟换速度）；chunk=32 版本在根目录。
- 上游与 2.7 同源（csukuangfj/k2fsa-zipformer-bilingual-zh-en-t，"internal dataset"），许可同样不明。
- **ncnn 路线里唯一"真正的中英混说"小模型**。作为"多语种+低体积"的 c 档第二选择（onnx 找不到同代数）。

### 2.9 streaming-zipformer-zh-14M（ncnn/onnx 共版）

### 2.10 streaming paraformer 双语/三语 int8（sherpa-onnx）

- 按住说话适配：★★★★★ —— 中英双方案里唯一"原生流式 + 官方可追溯许可 + ≤250M"。

### 2.11 streaming-zipformer-ar_en_id_ja_ru_th_vi_zh-2025-02-10

### 2.12 SenseVoice-Small int8（zh-en-ja-ko-yue）

## 3. 场景推荐

### a) 中文效果优先
1. **第一选择：`streaming-zipformer-zh-int8-2025-06-30`（~160M）**
   - 理由：所有已核实候选里"流式 CER 最好 + 体积可控 + 原生流式"三占（aishell-1 1.91 / WSpeech dev 5.71）。
   - 风险：① 训练数据商用性（WenetSpeech 10k h 限非商业下载）**必须先过 §5 许可证审计**；② 低端机 RTF 未实测，诶，0.15 是桌面值；③ 22 个 BPE id 2000 词表对 hyper/hot-word（应用名）偏弱——需验证是否更要 CTC+词图方案。
   - *合规兜底*：如果审计失败，同动力源的选项只剩"自购/自研数据重训"或"换 Apache 栈模型（FireRed2 体积放大 4.6 倍）"。
2. **第二选择：`streaming-zipformer-ctc-zh-int8-2025-06-30`（155M）**
   - 与 1 同数据、同模型家族，RTF 略优（0.14 vs 0.15）、partial 需做 CTC blank 归一化。适合把 transducer 留给效果档、CTC 兜低配。
3. **效果优先备选（非流式对照组）**：`FireRedASR2 CTC int8`（740M，方言覆盖强）或 `SenseVoice int8`（228M，带标点/ITN）——用于"按下后整段解码出高质量 final"的重评价场景，不满足按住说话的本征体验。

### b) 体积/低端机优先
1. **第一选择：`streaming-zipformer-small-ctc-zh-int8-2025-04-01`（25M）**
   - 理由：25M + RTF 0.04；HF 独立 `apache-2.0` 标签；sherpa-onnx runtime 19.7MB → **总包线 ~45MB** 量级可做到（模型 assets 直接内嵌）。
   - 风险：① CER 0 参考数据 → **必须自测**；② 训练语料未公开（若与 multi-zh-hans 混炼同源，许可审计仍要跑）；③ byte-BPE vocab=1000 词表面小，数字/日期归一化要做校验。
2. **第二选择：`streaming-zipformer-multi-zh-hans-2023-12-12` transducer int8（69M）**
   - RTF 0.088 + "non-streaming CER 有榜"（aishell-1 2.91/3.04、WSpeech dev 9.32）——是"小模型里的效果兜底"。流式 CER 未公布→同样实测。
3. **极限体积**：ncnn `zh-14M`（tar 22.2MiB）+ ncnn runtime 4.4MB → **APK ~32MB** 量级；每次都无 CER 数据，纯实测驱动。若跑过 A/B，是"超轻机型"最稳路线。
4. 若需"中文+说英语"但栈愿回到 2023 年模型，配合 `small-bilingual` chunk 目录（§2.8），但语义/许可双疑点。

### c) 中英混说优先
1. **第一选择：流式 paraformer 双语 int8（span zh+en）≈226M**
   - 理由：唯一"官方可追溯 Apache-2.0 + 原生流式 + 同时覆盖中英"三条全绿的候选；无 timestamps 是展示层问题（可以后加。）。
   - 风险：① bigger model 档的训练语料未披露（Apache 许可证不等于数据合规，但相对低风险）；② RTF 0.15 同 zipformer-large 一档，低端机要验证。
2. **第二选择：`ar_en_id_ja_ru_th_vi_zh-2025-02-10`（≈323M，8 语种）**
   - 理由：zh+en+6 语种一站式；体积 1.4× paraformer。
   - 风险：**官方文档未收录**（无 CER/无训练数据/无法则），HF 卡 license 字段为空——上路前必须做一轮"上游 recipe 找主办方问"的动作（例如 GitHub issues 找作者）。
3. **同时再报备设定**：**现役 ncnn 双语（134.6MiB）**——它的语料与许可不明（§2.7），继续使用等于长期把"内部数据集"带在身边，建议年底前用 paraformer 路线替代作为中英混说主场，ncnn 这条**只剩"过渡期"用途**（或 ncnn zh-14M 纯中文兜底）。

### 6.2 指标（每条语料 x 每模型）
1. **中文 CER**（归一化后整句计算；partial 不参与）
2. **首字延迟**：按下→第一个 partial 出现的 ms（中位 + P95，n≥50）
3. **partial 稳定时间**：partial 文本不再摇摆（前缀不变）到达 final 95% 匹配的时间点分布
4. **松手→final 延迟**：松手事件→final 回调 ms（中位 + P95）
5. **RTF**：decode 耗时/音频时长（分低端机-A55 与主流机-A7x 两档）
6. **内存 PSS**：`Debug.getMemoryInfo` native PSS 峰值/均值
7. **10 分钟连续录音温升**：每 60s 采样 CPU/battery 温度与帧率掉的衰减曲线

其余硬性要求：全部在离线模式下、模型 assets→filesDir 拷贝路径（与现役一致）；低端机按 2GB RAM / Android 11（A5x/A55），主流机按 A7x/A8x。

### 6.3 语料集（每类≥30 句，含叠加 SNR 版）
| # | 语料 | 针对性 |
|---|---|---|
| 1 | 安静近讲 20cm | 基准 CER |
| 2 | 嘈杂街道/咖啡厅（SNR≈10/0dB） | 降噪稳定性 |
| 3 | 远场 2–3m | 近远场一致性 |
| 4 | 快速连读（1.3×） | RTF 压力 |
| 5 | 中英混读（"打开 Wi-Fi，把 Bluetooth 关掉"级） | code-switch 断点 |
| 6 | 数字/验证码/日期串 | ITN 归一化 |
| 7 | 专有名词（联系人/应用名 30 个） | hotwords 支持差异（Qwen3 才有显式 hotwords） |
| 8 | 应用指令（"打开相机/暂停播放"，≤6字） | 指令召回 |
| 9 | 尾字易丢句（"停/继续/返回/给张怡"，≤5 字） | 松手截断损失 |
| 10 | 30 秒长句（连续读+若干停顿） | endpointing/内存爬升 |

### 6.4 决策判据（示例阈值，可调）
- CER：候选在语料 1/2/5/8 综合不超过 Baseline −50%（最好 −60%）
- 首字延迟：≤ 400ms（P95）
- 松手→final：≤ 300ms（P95）
- RTF：低端机 ≤ 0.6（纯 CPU int8）
- PSS：< 250MB 峰值（含模型）
- 温升：10 分钟 ≤ +8℃
